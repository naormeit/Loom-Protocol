When many AI agents want the same thing, Loom decides who gets it.

Loom is a pre-transaction coordination layer. Agents declare their intent first; Loom checks it, grants exactly one atomic lock, and tells every other agent how to retry. No duplicate holds, no retry storms.

The problem we think is coming

Autonomous agents will race for the same scarce thing.

Tickets, limited drops, booking slots, GPU capacity: when many agents spot the same opportunity at once, the vendor sees a burst of near-identical requests. That can mean duplicate holds, retry storms, and agents that lose without any machine-readable way to try again.

This is still a hypothesis. We are talking to people who build and run agents to find out where it really hurts, and we will change course if it does not.

How it works

Declare intent. One lock. Clear answers.

  1. 01 Agents declare intent

    Each agent sends a packet, optionally signed: who it is, what it wants, which resource, and how long to hold it.

  2. 02 Loom checks, then decides

    It validates the packet, verifies authority, screens the intent, and attempts one atomic lock on the resource.

  3. 03 One winner, clear answers

    One agent gets a 201 lock. Every other agent gets a 409 with a retry suggestion it can act on in code.

Working today

Local MVP

A local gateway and lock kernel, a Python SDK, packet signing with replay protection, and a live demo with real responses. The test suite passes.

In progress

Running on Azure

The same flow on Azure OpenAI, Content Safety and Cosmos DB with live evidence. Hosted so far in local mode only.

Not yet

Validation and hardening

Customer validation, pricing, public-key signatures and an audit trail. Safety screening is a keyword check locally, not real screening.
